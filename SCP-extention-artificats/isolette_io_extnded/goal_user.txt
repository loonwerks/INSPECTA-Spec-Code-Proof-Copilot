User-mode workflow
==================

1. Read the user request and identify the intended construct:
   - process definition;
   - thread definition;
   - process/thread containment;
   - input or output ports;
   - DataPort or EventDataPort choice;
   - connections;
   - scheduling, dispatch, period, domain, or binding attributes;
   - GUMBO contract attachment location;
   - Scala/Slang compatibility expectation;
   - seL4/Microkit/Rust/Verus process compatibility expectation;
   - verification or repair task.

2. Load only the relevant frozen rule-book sections needed for the request.
   - Prefer `final-combined-process-meta-rule-book.md` for broad generation.
   - Prefer specialized final rule books for narrow edits.
   - Use `final-process-apply-rules-prompt.md` as the prompt template for generation.

3. Inspect the active repository context before editing:
   - target SysML package and namespace;
   - existing process/thread naming style;
   - existing port and data type declarations;
   - existing connection syntax;
   - active HAMR/JVM profile expectations from active project files only;
   - model-level `sysml-logika` compatibility from the active `isolette/sysml-logika` tree when verification is requested.

4. Generate or repair the requested artifact using the frozen rules.
   - Preserve traceability to the English source, requirement ID, source file, or user-provided description.
   - Report the applied rule IDs in comments or in a companion note when appropriate.
   - Do not invent unsupported SysML v2, HAMR, GUMBO, Scala/Slang, seL4, Rust, or Verus syntax.
   - Prefer minimal edits to the active user-requested file.

5. If editing active SysML files, keep profile compatibility in mind:
   - Main HAMR/JVM codegen profile uses active project files under `isolette/sysml`.
   - Model-level integration Logika uses `isolette/sysml-logika`.
   - Do not blindly copy time-unit, DataPort refinement, or Microkit-only attribute syntax between profiles.
   - Do not add `HAMR::Microkit_Language` attributes to JVM profile files unless the active library defines them.

6. Verification policy:
   - Do not use clean-profile snapshots, frozen verification profiles, or verifier outputs from `eva-results` / `eval_results`.
   - Prefer active-project verification commands from `isolette/sysml/sireum_verification_plan.txt`, `isolette/sysml/bin/run-hamr.cmd`, and active repository scripts when they are safe for the requested task.
   - If a broad active sourcepath is contaminated, create a fresh temporary verification workspace from active project files only; do not copy an old clean-profile snapshot.
   - Use `isolette/hamr/slang/bin/run-logika.cmd` for maintained code-level Logika.
   - Use `sireum hamr sysml logika --sourcepath /home/amertahat/SPEC_CODE_PROOF/isolette/sysml-logika` for model-level integration Logika.
   - If verification fails, classify the failure and propose the smallest repair before editing generated code or application logic.

7. Do not rerun training by default.
   - Do not rebuild the process-definition dataset.
   - Do not rewrite candidate/extracted rule books.
   - Do not overwrite final rule books.

8. Validation rule for accepting user-mode generated or repaired artifacts.
   - Do not accept a generated or repaired process-definition artifact merely because it is textually similar to an example.
   - All GUMBO contracts required by the system description PDF or TXT source, especially the Steve Miller / FAA REMH text when present, must be traced into a checklist aligned with the GUMBO contract categories and list structure used in `Gumbo_FSE_agent_Plan.txt` / `FSE_agent_Plan.txt`.
   - Every required contract item from that checklist must either appear as a `language "GUMBO" /*{ ... }*/` contract on the correct project-owned behavioral thread or be explicitly marked not applicable with a source-backed reason.
   - Testing must include GUMBO contract coverage, not only process/thread/port syntax coverage. Check initialize contracts, compute contracts, compute cases, assumptions, guarantees, integration assumptions/guarantees when used, and contract attachment location.
   - All processes required by the English/PDF/TXT system description and repository architecture must be defined, all required process-owned threads must be defined, all required ports and connections must be present, and all process/thread/GUMBO artifacts must be included in structural checks.
   - All available verification gates must pass before acceptance: HAMR/Sireum type checking or code generation, code-level Logika, model-level Logika with the compatible sourcepath/profile, and Verus/GUMBOX/proptest when the target and repository provide them.
   - If any required process, thread, port, connection, GUMBO contract, or verifier gate is missing, failing, or only planned, report the artifact as provisional or human-review-required rather than accepted.
   - If semantic/cosine scoring falls back from an embedding or cosine-distance implementation to a proxy metric, report to the user why the fallback was used, which dependency or access was unavailable, where the fallback result is recorded, and whether structural/GUMBO/verification evidence is sufficient for acceptance.
