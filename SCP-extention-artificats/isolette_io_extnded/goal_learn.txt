Important algorithm interpretation
==================================

Follow the paper's two-phase SCP Meta-Rule algorithm, adapted to a process-definition-focused train/test protocol.

Definitions:

- R: natural-language requirements, English engineering descriptions, and architecture/process descriptions.
- G: golden examples, each pair containing English source text and a verified SysML v2 / HAMR process-definition artifact or related formal artifact.
- M: retained process-definition Meta-Rule library.
- C: verified process definitions and related specifications produced by the workflow.
- F: flagged failures.
- B: bounded repair budget, including time, token, and repair-cycle limits. Default to 20 minutes, 560,000 tokens for inputs, 19 million cached tokens, and 100,000 output tokens. If these limits are reached, stop and ask whether the user wants to approve additional budget before continuing.
- epsilon: semantic-distance threshold controlling how far a generated process-definition formalization may be from the golden formalization.
- epsilon_struct: structural-distance threshold for process-definition features such as process/thread/port/connection coverage.
- tau: acceptance threshold for retaining a rule.
- V(candidate, B): verification function using available HAMR, Logika, Sireum, Verus, or repository-specific test infrastructure.

The paper uses semantic distance as a generalization control, not as a literal text-matching objective. For process definitions, do not minimize epsilon blindly. Too-small epsilon over-specializes a rule to one process name or one port list; too-large epsilon admits broad rules that may produce invalid process structures. Calibrate epsilon as a practical operating point that balances reusability, structural correctness, verification success, and bounded repair cost.

Use this semantic epsilon schedule unless repository evidence suggests a better one:

- Start epsilon = 0.01.
- Evaluate candidate rules on the training/calibration set.
- Promote only candidates that improve semantic alignment, structural correctness, and verification outcome.
- If verification succeeds and repair cost remains within budget, try widening epsilon gradually to 0.05, 0.1, 0.3 and at most 0.5.
- Do not expand epsilon beyond 0.5 unless the user explicitly approves.
- If a wider epsilon reduces verification success, reduces structural correctness, or increases repair cost beyond budget, revert to the best previous epsilon.
- Record every epsilon value, score, verification result, structural score, and decision.

Use this structural scoring schedule for process definitions:

- Start epsilon_struct = 0.00 for mandatory structural fields that must exactly match the repository convention. This is a separate explicit structure-check gate, not the semantic/cosine-distance epsilon schedule.
- Allow epsilon_struct up to 0.1 for non-critical naming or formatting differences only when the model type-checks and preserves traceability.
- Mandatory fields should include process/thread containment, port direction, port type, connection endpoints, and required HAMR attributes.
- Do not accept a generated process definition that passes semantic similarity but omits required process/thread/port/connection structure.
- Make sure all requirements are defined and verified.

Testing/evaluation memory isolation
===================================

Testing-set evaluation must be isolated from training truth values and from held-out formal process definitions. The purpose is to prevent faked results caused by old snapshots, memorized golden files, or test files that already contain the process definitions being evaluated.

Use three separate memories/directories during testing:

1. Candidate-rule memory:
   - Contains only the frozen candidate rule books and prompts being evaluated.
   - Must not contain held-out golden SysML, train/test truth manifests, score tables, verification snapshots, or generated outputs from earlier runs.

2. Sanitized test-input memory:
   - Contains the English/system input given to the candidate rules.
   - For process-definition tests, the SysML files in this memory must not include the process, thread, port, connection, scheduling, or GUMBO process artifacts being tested.
   - Sanitized test SysML may include only the surrounding system definition, package shell, imports, data model references, and other non-answer context needed to compile or locate the target subsystem.
   - If a source test file contains the process definition under evaluation, create a redacted copy for generation by removing that process-definition answer before the candidate rules run.
   - The generator must use only candidate-rule memory plus sanitized test-input memory.

3. Evaluator-only truth memory:
   - Contains held-out golden/reference process definitions, expected structural facts, expected GUMBO coverage, semantic embeddings, verification outcomes, and scoring records.
   - This memory is read only by the evaluator after candidate generation is complete.
   - It must never be mounted, copied, searched, embedded into prompts, or otherwise exposed to candidate generation.

Evaluation sequence for each held-out test case:

1. Build the sanitized test-input memory first.
2. Create the isolated embedding/scoring workspace before any truth files are accessible.
3. Run embedding/span extraction for sanitized test inputs and candidate-rule text in that isolated workspace. This workspace must not contain hidden process definitions.
4. Generate the candidate process artifact using only the candidate rule book and sanitized test-input memory.
5. Freeze the generated candidate artifact, then embed/extract spans for the generated candidate in the same isolated scoring workspace.
6. Only after generation and generated-candidate embedding are frozen, compare the generated artifact against evaluator-only truth memory for semantic distance and structural coverage.
7. Run verification on a fresh temporary verification workspace built from active project files plus the generated candidate artifact. Do not use old clean-profile snapshots or previous verification outputs.
8. Retain a candidate rule only if both gates pass:
   - semantic gate passes under the configured embedding/cosine-distance policy; and
   - verification gate passes under the configured HAMR/Sireum/Logika/Verus or repository-equivalent checks.
9. If either semantic or verification fails, reject the candidate rule or mark it for repair/human review. Do not use evaluator-only truth to patch the rule before recording the failure.

Phase 5: Process-definition scoring
===================================

Use the repository's cosine-distance or semantic-similarity function from the tool folder. If several functions exist, choose the one most aligned with the paper's DISTANCE(g_hat, g_g) concept and document the choice.

Use `isolette/sysml/process_semantic_distance_strategy.md` as the controlling semantic-distance method. The strategy requires actual embedding vectors for actual cosine distance, and it defines process/thread/port/connection/scheduling/GUMBO span extraction so evaluation does not remain limited to GUMBO blocks.

Before scoring, enforce testing/evaluation memory isolation:

- The embedding/scoring workspace for candidate outputs must not contain the held-out process definitions except inside evaluator-only truth memory used after generation is frozen.
- Candidate generation must consume sanitized test inputs that do not include the target process/thread/port/connection/scheduling/GUMBO answer.
- If a SysML test input is needed for context, redact the answer process definitions from the generation copy. It may keep package declarations, imports, system definitions, data types, and non-answer architecture context.
- Do not compare against golden/reference artifacts until the candidate output is already written and immutable for that test iteration.
- Do not reuse embedding JSON, distance tables, verification logs, or score tables from previous runs as evidence for a new candidate.

Semantic-distance API approval for this experiment:

- The user explicitly approves using OpenAI's official embeddings API/function when that is the available implementation for semantic or cosine distance.
- The user explicitly approves running `embedding_distance.py` with OpenAI embeddings API access for relevant rule-evaluation comparisons.
- This approval includes sending the relevant local SysML v2, GUMBO, English-description, generated-artifact, and golden/reference artifact text needed to compute embedding distances.
- Actual cosine distance means embeddings were produced by the approved embedding implementation. Codex may compute cosine from already-computed numeric vectors, but it must not fabricate vectors from text and label that as actual embedding distance.
- Use the smallest relevant text spans needed for each comparison, such as matching process fragments, GUMBO blocks, generated artifacts, and golden/reference artifacts. Do not upload unrelated repository content.
- At run time, Codex should request escalation for this command when network/API access is required, state that the user has approved OpenAI embeddings data transfer for `embedding_distance.py`, and specify that only the smallest relevant comparison spans may be sent. Do not skip the embedding run solely because it requires this approved escalation request.
- Record the command/tool used, model/function used when known, compared files or blocks, output path, and resulting distances in `eva-results/`.
- Record which workspace was used for candidate generation, which workspace was used for sanitized embeddings, and which evaluator-only truth path was used after generation.
- If this Codex runtime rejects the escalated API call because external transfer of private SysML/GUMBO text is not allowed, run the same `embedding_distance.py` commands from a user-controlled terminal where the OpenAI embeddings API is allowed, then copy the resulting JSON files into `isolette/sysml/eva-results/`. This is still actual embedding cosine distance if the external terminal run used the approved embeddings API; record that Codex could not perform the transfer directly and that the user-provided JSON files were imported.
- Preferred helper script for the external-terminal workflow: `.venv/bin/python isolette/sysml/tools/run_external_embedding_distance.py`. This loads `.env`, runs the Monitor and Regulate embedding-distance smoke tests, writes JSON outputs to `isolette/sysml/eva-results/`, and records `embedding_distance_external_run_manifest.json`.
- External-terminal embedding commands must use run-specific temporary input/output paths that preserve the three-memory split:
  - sanitized test inputs and generated candidates in a scoring workspace;
  - evaluator-only truth files mounted/read only after generation;
  - embedding JSON written to the current run's `eva-results/` scoring output.
  Do not run smoke-test commands that compare active full SysML files against golden process files and then reuse those results as held-out evaluation evidence.
- If no API key in .env file, network access, package dependency, or embedding model is available, fall back to a local token-vector cosine metric and record that fallback explicitly. Also report directly to the user why the proxy/fallback was used, which required embedding/cosine-distance dependency was unavailable, and how the fallback affects confidence in accepting or rejecting the rules.

Use the verification plan from sireum_verification_plan.txt and any repository-specific scripts.

Default process-definition verification sequence:

1. Parse/type-check the SysML v2 process definition using the repository-equivalent command.
2. Regenerate artifacts from the SysML model.
   - For JVM/Scala/Slang: run `isolette/sysml/bin/run-hamr.cmd JVM` or the repository-equivalent command.
   - For seL4/Microkit: run `isolette/sysml/bin/run-hamr.cmd Microkit` only when the user or experiment target requests Microkit.

   - Build any verification workspace freshly from active project files plus the generated candidate artifact.
   - Do not use old clean-profile snapshots, `verification-profiles/`, prior HAMR outputs, prior Logika outputs, or previous repair directories as verification evidence.

Phase 7: Rule acceptance and rejection
======================================

Retain a candidate process-definition rule only when all applicable criteria are satisfied:

1. It is supported by training examples or by an explicit training/context document.
2. It improves or preserves semantic alignment under the current epsilon.
3. It improves or preserves structural correctness under epsilon_struct.
4. It passes the verification/type-checking gate within budget B when verification is available.
5. It generalizes to enough training/calibration examples to meet tau.
6. It does not reduce held-out process-definition performance after rule-book freezing.
7. It is auditable, specific, and not merely vague advice.
8. It does not introduce unsupported SysML v2, HAMR, GUMBO, Scala/Slang, seL4, Rust, or Verus syntax.
9. It preserves process/thread/port/connection semantics from the English text.
10. It is approved or marked for human review when the paper's algorithm calls for human-in-the-loop refinement.

Additional testing-set retention rule:

- Candidate rules are retained only if the held-out generated artifacts pass both the semantic gate and the verification gate in the isolated test workflow.
- A rule that passes semantic distance but fails verification is rejected or marked for repair; do not retain it as successful.
- A rule that passes verification but fails semantic distance is rejected or marked for repair; do not retain it as successful.
- A rule evaluated using snapshots, unredacted test files containing the answer process definitions, stale embedding JSON, stale verification logs, or reused clean-profile outputs is invalid and must be rerun from isolated memories.

Acceptance validation rule for GUMBO, process completeness, and scoring:

A learned rule book is not acceptable until the evaluation report proves all of the following with file paths, requirement IDs or source-text anchors, and verifier outputs:

- All GUMBO contracts required by the system description PDF or TXT source, especially the Steve Miller / FAA REMH text when present, have been extracted into a checklist aligned with the GUMBO contract categories and list structure used in `Gumbo_FSE_agent_Plan.txt` / `FSE_agent_Plan.txt`.
- Every required contract item from that checklist is either implemented as a `language "GUMBO" /*{ ... }*/` contract on the correct project-owned behavioral thread or is explicitly marked not applicable with a source-backed reason.
- The test/evaluation set includes GUMBO contract coverage, not only process/thread/port syntax coverage. It must check initialize contracts, compute contracts, compute cases, assumptions, guarantees, integration assumptions/guarantees when used, and contract attachment location.
- The final evaluation report includes a GUMBO coverage table showing source requirement text or ID, expected contract family from `Gumbo_FSE_agent_Plan.txt`, SysML/GUMBO attachment file and thread, verification command, verification result, and any repair history.
- All processes required by the English/PDF/TXT system description and repository architecture are defined, all required process-owned threads are defined, all required ports and connections are present, and all process/thread/GUMBO artifacts are included in structural scoring.
- All available verification gates pass for the accepted rule book and generated/repaired artifacts: HAMR/Sireum type checking or code generation, code-level Logika, model-level Logika with the compatible sourcepath/profile, and Verus/GUMBOX/proptest when the target and repository provide them.
- If any required process, thread, port, connection, GUMBO contract, or verifier gate is missing, failing, or only planned, the rules must remain rejected, provisional, or human-review-required rather than accepted.
- If the experiment falls back from an embedding/cosine-distance implementation to a proxy metric, the agent must report to the user why the fallback was used, what exact dependency or access was unavailable, where the fallback result is recorded, and why structural/GUMBO/verification evidence is still sufficient or not sufficient for acceptance.

Reject or revise a rule when:

- it only memorizes one process example and does not generalize;
- it incorrectly maps English components to process boundaries;
- it incorrectly maps process descriptions to threads;
- it omits mandatory ports or connections;
- it creates invalid DataPort/EventDataPort selections;
- it causes verifier or type-checker failures;
- it requires excessive repair;
- it conflicts with repository conventions;
- it invents unsupported SysML v2 or HAMR syntax;
- it hides a toolchain/profile problem by weakening project contracts;
- it leaks test-set information into training.

Record all decisions in:

- rule-books/rule-change-log.md
- rule-books/rejected-process-definition-rules.md
- rule-books/rejected-process-definition-rules.json

Phase 9: Iterate
================
